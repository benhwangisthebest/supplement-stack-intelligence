## daily-checkin (v10)
Closes the platform's open recommendation loop with a **gamified daily check-in + feedback loop**. A daily check-in captures **adherence** (which stack items were taken) + a **1–5 rating on active goals**; a pure `lib/checkin` engine derives a **consistency** metric (premium heatmap, no points/badges), **correlational** outcome aggregates (avg goal rating on taken-vs-not days), and a **bounded, min-sample-gated feedback signal** that nudges the existing `generateProtocol` ranking. Architecture is **additive** with a key safety decision: the feedback signal is inserted as a ranking key **strictly below grade** (`labSignal → grade → feedback → composite → name`), so self-reported feedback is **evidence-subordinate by construction** — it can only break ties within an equal grade and can **never override evidence**. This is *proven, not asserted*: a **no-feedback regression test** shows `generateProtocol` output is byte-identical without a signal, and that a max feedback never lifts a lower grade above a higher one. Consistency also feeds the **v9 identity** `dataDepth`, unifying the two gamification features. All outcome/side-effect copy is **correlational + non-diagnostic** (honesty sweep); the side-effect/note field is **display-only**. Built via Plan-Plus → PDCA (Do ×3 modules, Check **99%**, **0 iterations**, QA **PASS**). Success criteria **10/10**; **340/340 unit** (+29) incl. feedback-regression + honesty; `next build` OK; L1 auth-guard 2/2 + L2 `/stack-lab` redirect 1/1 runtime-verified live, authed L3 env-gated (`E2E_LIVE`, needs `0006` applied). First milestone to intentionally break the no-migration / no-engine-edit streaks — done via **one additive migration** (`0006_checkins`, RLS + unique(user,date)) and **optional, backward-compatible** engine inputs, keeping all prior v3/v4/v5/v9 suites green. No new dependencies. **Deferred to v11:** proactive advisor change-proposals, side-effect engine, reminders/notifications, wearable import, longitudinal trend charts, authed live-E2E provisioning.

## food-pairings (v12)
Answers the everyday question the Library never addressed: **what should I eat with this?** A curated **supplement↔food** dataset delivers absorption-focused guidance — *pairs well with* (vitamin D + a fat-containing meal, creatine + carbohydrates, curcumin-style synergies) and *best to space apart* (zinc + phytates/calcium, caffeine + caffeinated drinks) — each with mechanism, timing, and an evidence grade. Architecture **Option C (pragmatic)**: rather than build a parallel domain, the feature **extends the existing interactions engine** with a `supplement-food` kind + `direction` (`synergy`/`avoid`), so guidance rides the established `findInteractions → InteractionFinding → to-flags → DraftFlag` pipeline and reaches **Library + Stack Lab + advisor with zero caller changes** (`ALL_INTERACTION_RULES` becomes the engine default). The load-bearing risk defense is **tone**: reusing a model literally named `InteractionRule` for *beneficial* pairings risked rendering "pairs well with citrus" as an alarm — so synergy is pinned to `info` by an explicit guard in `mapSeverity` and given its own `safetyCopy.foodSynergy` + dedicated `FoodPairingSection` UI, both **test-enforced** ("never escalates food guidance to critical"). Built via Plan-Plus → PDCA (Do ×4 modules, Check **99.5%**, **0 iterations**). Success criteria **2/4 met, 2/4 partial, 0 unmet**; **374/374 unit** (+15) incl. schema/integrity/banned-language sweep; **runtime-verified across all 15 catalog pages** (9 with data, 6 graceful empty state). **No migration, no new dependency** — seed-as-code only.

**Honest caveats:** (1) SC-2 partial — coverage is 9/15 supplements, per the curation rule that only well-documented pairings ship and absence never implies "no effect". (2) SC-4 partial — making `ALL_INTERACTION_RULES` the engine default **changed what Stack Lab emits** (a lone berberine now yields a food info flag where it previously yielded none), requiring **6 existing tests** to be updated (4 scoped to `SEED_INTERACTIONS`, 2 re-asserted on category rather than exact counts); intent preserved but the behavior change warrants human review. (3) QA phase not run. **Deferred:** AI-generated pairings, diet/allergy personalization, quantitative dosing math, meal plans, community data.
